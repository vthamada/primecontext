# PrimeContext v0.1 — Implementation Architecture

**Status:** Accepted for v0.1 implementation  
**Date:** 2026-08-11  
**Source of product requirements:** `docs/specification/product-architecture-specification-v0.1.md`

## 1. Objective

Turn the PrimeContext product specification into the smallest production-shaped implementation that proves the core thesis without pulling v0.2+ retrieval features into v0.1.

The v0.1 vertical slice is:

```text
Repository + config
      ↓
Safe filesystem/Git discovery
      ↓
Semantic Repo Map
      ↓
Task definition
      ↓
Context Budget policy
      ↓
Validated Task Capsule
      ↓
Agent/user consumption
      ↓
Validated Compact Handoff
      ↓
Metric records / benchmark input
```

v0.1 does **not** implement Document Catalog retrieval, CodeGraph integration, Context Scout ranking, pruning, snapshots, Experience Store, MCP, hosted services, embeddings, or a web UI.

## 2. Technical stack

### Runtime

- Node.js 22+ supported.
- Node.js 24 LTS is the preferred development/runtime line for new installations.
- TypeScript, strict mode.
- ECMAScript modules (ESM).
- npm workspaces; no mandatory alternative package manager.

### Contracts and validation

- JSON Schema is the language-neutral contract format.
- v0.1 runtime validation uses contract-specific structural validators with JSON Schema-compatible exported contracts; a generic schema engine is deferred until contract scale justifies it.
- External inputs are always validated at package/CLI boundaries before entering the core domain.
- Schema changes are versioned and treated as API changes.

### Testing

- Node's native test runner against compiled TypeScript output.
- TypeScript typecheck is an independent verification gate.
- Tests prefer real filesystem/Git fixtures over mocks when practical.

### Persistence

- JSON/JSONL files for v0.1 runtime state.
- SQLite is explicitly deferred until a real query/indexing requirement appears.
- `.primecontext/` is local generated state and is ignored by Git by default.
- `primecontext.config.json` is repository configuration and is intended to be committed.

## 3. Physical package boundaries

The product specification lists many conceptual components. v0.1 deliberately uses fewer physical packages to avoid premature fragmentation.

```text
packages/
  schemas/      language-neutral contracts + validators
  core/         domain types, budget policy, capsule/handoff creation, metrics contracts
  adapters/     filesystem + Git implementations of core ports
  repo-map/     deterministic semantic repository map generation
  benchmark/    A/B record model and comparison skeleton
  cli/          public command-line surface
```

Future concepts remain modules/interfaces until independent lifecycle or dependency pressure justifies a package split.

### Dependency direction

```text
schemas
   ↑
 core
 ↑  ↑
adapters  benchmark
   ↑        ↑
 repo-map   │
      \     │
        cli
```

Rules:

1. `schemas` depends on no PrimeContext package.
2. `core` may depend on `schemas` but never on adapters or CLI.
3. `adapters` implements ports declared by `core`.
4. `repo-map` consumes `core` contracts and adapter capabilities.
5. `benchmark` consumes metrics/domain contracts from `core`.
6. `cli` is composition root; no other package imports it.

## 4. Core domain contracts

### 4.1 TaskType

Normalized JSON values:

- `small_ui`
- `small_code_fix`
- `module_feature`
- `integration`
- `qa`
- `orchestration`

### 4.2 ContextBudget

```ts
interface ContextBudget {
  initial_tokens: number;
  soft_limit_tokens: number;
  hard_limit_tokens: number;
}
```

Invariants:

```text
0 < initial_tokens <= soft_limit_tokens <= hard_limit_tokens
```

The product specification supplies experimental initial and soft limits. v0.1 adds one implementation convention: unless overridden, the hard limit is `2 × soft_limit_tokens`. This convention is configuration, not a product claim, and may change after benchmark evidence.

### 4.3 TaskCapsule

Required:

- `schema_version`
- `task_id`
- `goal`
- `task_type`
- `boundaries`
- `acceptance`
- `context_budget`

Optional but supported in v0.1:

- `module`
- `priority`
- `decisions`
- `contracts`
- `documents`
- `code_targets`
- `worktree`
- `metadata`

`worktree` carries branch/root/head metadata when available, satisfying the worktree-awareness requirement without making Git mandatory.

### 4.4 CompactHandoff

Required:

- `schema_version`
- `task_id`
- `status`
- `changed_files`
- `tests`
- `risks`
- `next_unblocked`

Optional:

- `commit`
- `interfaces_added`
- `decisions`
- `artifacts`
- `metrics_ref`

Handoffs are bounded structured results; raw transcripts never become part of this contract.

### 4.5 SemanticRepoMap

```ts
interface SemanticRepoMap {
  schema_version: string;
  generated_at: string;
  repository: RepositoryIdentity;
  modules: RepoModule[];
  summary: RepoSummary;
}
```

Each module has:

- stable `id`;
- `path`;
- inferred `kind`;
- compact `role`;
- `evidence` explaining the deterministic inference.

v0.1 semantics are deterministic and evidence-backed. They are derived from workspace/package manifests, conventional directory roles, and Git metadata. v0.1 does **not** pretend to infer callers/callees or architecture semantics that require CodeGraph/AST analysis.

## 5. Ports

Declared in `@primecontext/core`:

```ts
interface FileSystemPort {
  walk(root: string): Promise<DiscoveredPath[]>;
  readText(path: string, maxBytes?: number): Promise<string>;
}

interface GitPort {
  inspect(root: string): Promise<GitState | undefined>;
}

interface MetricSink {
  record(metric: MetricRecord): Promise<void>;
}
```

Adapters are replaceable. The core never imports Node filesystem or child-process APIs directly except where a tiny utility is proven to belong in core.

## 6. Safe discovery model

Default excluded classes:

- `.env` and `.env.*`;
- credential/key/certificate patterns;
- `.git/`;
- `node_modules/`;
- generated build directories;
- `.primecontext/` runtime state;
- private dump/backup patterns.

Security behavior:

1. sensitive paths are rejected before content reads;
2. symbolic links are not followed during v0.1 discovery;
3. the map never emits names/content for blocked secret paths;
4. Git commands are executed without a shell;
5. failure to obtain Git state does not block filesystem mapping;
6. write-oriented integrations are out of scope for v0.1.

## 7. Repo Map inference

v0.1 recognizes these module kinds:

- `workspace_package`
- `source`
- `tests`
- `documentation`
- `configuration`
- `examples`
- `benchmarks`
- `other`

Inference priority:

1. workspace/package manifest metadata;
2. well-known directory semantics;
3. fallback to a compact neutral role.

The output is a semantic map of **roles and boundaries**, not a full file inventory.

## 8. CLI contract

Initial commands remain aligned with the product specification:

```bash
primecontext init
primecontext map
primecontext task <task-id>
primecontext inspect <task-id>
primecontext handoff validate <file>
primecontext benchmark
primecontext metrics
```

### `primecontext init`

Creates:

- `primecontext.config.json` if absent;
- `.primecontext/` runtime directory;
- generated-state ignore rules where safely possible.

Never overwrites user configuration silently.

### `primecontext map`

Generates `.primecontext/repo-map.json` and prints a compact summary.

### `primecontext task <task-id>`

Loads a task definition from either:

1. `--from <file>`; or
2. `.primecontext/tasks/<task-id>.json`.

Allocates/validates a budget, attaches Git/worktree metadata when available, writes `.primecontext/capsules/<task-id>.json`, and prints the path.

### `primecontext inspect <task-id>`

Reads and validates an existing capsule and prints a compact human-readable view.

### `primecontext handoff validate <file>`

Validates a handoff; exit code is non-zero on invalid input.

### `primecontext metrics`

Summarizes local JSONL metric records without making savings claims.

### `primecontext benchmark`

Compares Arm A and Arm B records when supplied. v0.1 reports raw deltas and quality outcomes; it does not label an optimization successful if the PrimeContext arm fails validation/quality gates.

## 9. Configuration

`primecontext.config.json` contains:

```json
{
  "schema_version": "0.1",
  "state_dir": ".primecontext",
  "exclude": [],
  "budgets": {
    "small_ui": {"initial_tokens": 3000, "soft_limit_tokens": 6000, "hard_limit_tokens": 12000},
    "small_code_fix": {"initial_tokens": 4000, "soft_limit_tokens": 8000, "hard_limit_tokens": 16000},
    "module_feature": {"initial_tokens": 6000, "soft_limit_tokens": 12000, "hard_limit_tokens": 24000},
    "integration": {"initial_tokens": 8000, "soft_limit_tokens": 16000, "hard_limit_tokens": 32000},
    "qa": {"initial_tokens": 6000, "soft_limit_tokens": 12000, "hard_limit_tokens": 24000},
    "orchestration": {"initial_tokens": 10000, "soft_limit_tokens": 20000, "hard_limit_tokens": 40000}
  }
}
```

All budget values are explicitly experimental and configurable.

## 10. Metrics model

`MetricRecord` captures only fields supported by the specification:

- input tokens;
- cached input;
- output tokens;
- tool calls;
- file reads;
- CodeGraph calls;
- context expansions;
- duration;
- selected context size;
- test status;
- review status;
- rework count.

`estimated_fields` explicitly identifies measurements that are estimates.

v0.1 does not invent a universal scalar formula for **Validated Work per Token**. The benchmark retains raw evidence until a defensible scoring methodology is validated.

## 11. Error model

CLI errors are classified:

- `CONFIG_ERROR` — invalid/missing configuration;
- `VALIDATION_ERROR` — schema/domain invariant failure;
- `SECURITY_ERROR` — blocked unsafe path or operation;
- `IO_ERROR` — filesystem failure;
- `GIT_UNAVAILABLE` — non-fatal where Git is optional;
- `BENCHMARK_ERROR` — malformed benchmark input.

User-facing messages are concise; verbose stack traces require an explicit debug flag.

## 12. Testing strategy

### Contract tests

- valid Task Capsule accepted;
- invalid Capsule rejected with useful path information;
- valid Handoff accepted;
- budget ordering invariant enforced;
- metric estimates must be labeled.

### Security tests

- `.env` never read or emitted;
- key/credential patterns excluded;
- symlinks skipped;
- path traversal cannot escape repository root.

### Repo Map tests

- workspace package recognized from `package.json`;
- docs/tests/config directories receive expected roles;
- Git metadata included when available;
- mapping still succeeds when Git is unavailable.

### CLI tests

- `init` is idempotent;
- `map` creates valid map;
- `task` creates valid capsule;
- invalid handoff returns non-zero;
- `inspect` rejects corrupt capsule.

### Benchmark tests

- A/B raw deltas are deterministic;
- quality regression prevents a positive optimization verdict;
- estimated metrics remain visibly marked.

## 13. v0.1 completion gates

v0.1 is complete only when:

1. all package builds/typechecks pass;
2. all tests pass;
3. generated schemas/contracts validate fixtures;
4. security exclusion tests pass;
5. CLI vertical flow works in a sample repository;
6. benchmark skeleton can compare two fixture runs;
7. a sanitized MaxSound-style task fixture can produce a Task Capsule;
8. no paid or remote service is required.

## 14. Deferred boundaries

The following are intentionally deferred but have explicit future attachment points:

- Document Catalog → future `ContextSource` implementation;
- Context Scout → consumes discovered candidates and emits ranked references;
- CodeGraph → adapter implementing code-intelligence port;
- Context Pruner → core policy after retrieval exists;
- Artifact Store → persistence port once large outputs exist;
- Snapshot Store → read-only external-state provider;
- MCP → thin integration over existing core/CLI capabilities;
- Experience Store → selective source, never a global memory dump.

No v0.1 package may embed assumptions that make these future components mandatory.
