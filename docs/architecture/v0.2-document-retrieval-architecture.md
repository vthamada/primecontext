# PrimeContext v0.2 Document Retrieval Architecture

## 1. Vertical slice

```text
CLI docs index
  -> safe Markdown collection adapter
  -> Core catalog construction
  -> schema validation
  -> bounded temporary file + final replacement

CLI docs search
  -> validate stored catalog and query
  -> collect the live permitted corpus again
  -> compare canonical catalog digest and source hashes
  -> Core lexical match/score/excerpt
  -> validate compact result
```

The live second collection is intentional. It avoids persisting source bodies or token indexes and makes freshness a prerequisite for returning content.

## 2. Package responsibilities

### `@primecontext/schemas`

- three v0.2 schemas and runtime validators;
- portable path, hash, array, count, and cross-field invariants;
- physical-contract generation and package exports.

### `@primecontext/core`

- Document Catalog, query, result, source-collection, and hashing-port types;
- catalog construction and canonical digest input;
- pure query normalization, filtering, scoring, conflict grouping, and excerpt construction;
- defensive cloning and validation at public boundaries.

Core does not import filesystem, Git, CLI, Node hashing, or vendor logic.

### `@primecontext/adapters`

- safe Markdown corpus collection using existing repository discovery/excludes;
- strict UTF-8 byte reads, before/after file checks, SHA-256 hashing, title/authority/module/topic inference, and sensitive-content blocking;
- Node implementation of the Core hashing port.

### `@primecontext/cli`

- strict argv parsing;
- composition with configured excludes and optional Git metadata;
- catalog serialization, bounded parsing, and safe replacement beneath `state_dir`;
- freshness comparison and JSON output.

No new package is created. `repo-map` and `benchmark` remain unchanged.

## 3. Data model

The persisted catalog is one bounded JSON object. It contains only metadata and hashes. Documents are sorted by canonical `/` path; arrays used as sets are unique and ordinally sorted. Summary totals are recomputed and validated.

`catalog_digest` is SHA-256 over a canonical, explicit-key-order JSON representation of the sorted document metadata. It excludes `generated_at` and aggregate discovery counters. Search separately compares eligible-candidate and omitted-document counts so a newly content-blocked document also makes the catalog stale. The digest changes for an added, removed, moved, reclassified, renamed, resized, or content-modified accepted document.

Source IDs are derived from canonical paths rather than content, so an edited document retains identity while its `source_hash` and catalog digest change.

## 4. Corpus collection

The adapter first calls the existing bounded walker. It selects only the conservative Markdown corpus described in the specification and orders candidates ordinally.

For every candidate it:

1. rejects sensitive/configured-excluded paths before reading;
2. rejects oversized candidates using discovery metadata;
3. revalidates every existing path component;
4. checks file identity and size before reading;
5. reads bounded bytes and decodes with fatal UTF-8 handling;
6. checks identity and size again;
7. blocks unsafe content without returning the match;
8. hashes the bytes and extracts bounded metadata.

Unexpected I/O and global-limit failures abort the operation. Individual oversized, invalid-UTF-8, binary, or content-blocked documents are omitted with aggregate counts only.

## 5. Catalog replacement

The CLI serializes and size-checks the complete validated catalog before touching the prior catalog. It writes a sibling temporary file with exclusive creation, flushes and closes it, revalidates the directory and destination, and renames it to the final path. Collection, validation, serialization, temporary creation/write/`fsync`, or rename failures do not intentionally replace the prior catalog. A failure after a successful rename cannot restore the prior bytes, and portable Node APIs do not provide a directory `fsync` or universal power-loss guarantee.

Only one writer is supported. Portable Node APIs cannot guarantee atomic replacement against a malicious same-user concurrent actor on every Windows filesystem; that remains explicit residual risk.

## 6. Live search

Search treats the catalog as untrusted external state:

1. validate the structured search query before catalog or corpus I/O;
2. enforce stored-catalog byte and structure limits;
3. validate every catalog field and cross-record invariant;
4. recompute and compare the stored digest;
5. collect the permitted live corpus independently of catalog paths;
6. construct a fresh in-memory catalog and compare digests;
7. run pure Core matching and validate the result.

Search fails with `CATALOG_ERROR` when freshness cannot be established. It never silently uses stale content.

## 7. Scoring

All distinct query terms are required. For each matching document, Core calculates an integer score from capped occurrences in title, path, modules, topics, and body, plus an exact-title-phrase bonus. Authority is not relevance; it is used only after score equality. Final tie-breaks are path and stable ID in ordinal order.

Core returns the fields and query terms responsible for a match. Excerpts are extracted from the first relevant source window, preserve 1-based start/end line provenance, contain at most six lines, collapse unsafe controls, and are truncated to 400 Unicode code points.

Potential same-normalized-title/different-hash conflicts are derived from the full validated catalog rather than the hit slice, so a small `--limit` cannot silently hide them.

## 8. Failure model

| Condition | Result |
|---|---|
| invalid query or schema-invalid catalog | `VALIDATION_ERROR` |
| unsafe path/content | `SECURITY_ERROR` or aggregate exclusion during indexing |
| malformed or structurally excessive catalog JSON | `CATALOG_ERROR` |
| catalog digest mismatch or stale live corpus | `CATALOG_ERROR` |
| missing, unreadable, oversized, or invalid-UTF-8 catalog file | `IO_ERROR` |
| other native filesystem failure | `IO_ERROR` |
| Git metadata unavailable | fail open; source hashes remain authoritative |
| individual oversized/invalid Markdown | omit and count |
| global count/byte/output limit | abort; do not replace catalog |

## 9. Compatibility and verification

The v0.1 configuration remains `schema_version: "0.1"`; its `exclude` array is reused. The six physical v0.1 contracts and all existing commands remain unchanged.

Verification proceeds from focused schema/Core/adapter/CLI tests to a disposable vertical smoke, package dry run, typecheck, complete tests, build, link check, and `git diff --check`. Node.js 22 is the minimum supported runtime; available active lines should be exercised without claiming untested platforms.
