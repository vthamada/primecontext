# PrimeContext v0.3 consolidation specification

**Status:** ACCEPTED IMPLEMENTATION SCOPE
**Date:** 2026-08-14
**Baseline:** `80bf4f08b6da7b74368b105215cc7a7d91f17629`

## 1. Purpose

This specification authorizes a compatibility-preserving consolidation of the
implemented v0.3 Proof-Carrying Context Compiler. It corrects demonstrated
semantic, state-integrity, performance, and agent-output defects. It does not
authorize a new product capability or weaken any v0.1/v0.2 contract.

The implementation must remain local-first, deterministic, bounded, safe with
optional adapters absent, and useful through the safe filesystem/document
fallback alone.

## 2. Non-goals and independent gates

This consolidation does not authorize MCP, embeddings, learned or semantic
ranking, network access, hosted services, remote telemetry, automatic agent
execution, a web UI, an external vault connector, or a new package.

The following remain independent human/evidence gates and cannot be fabricated
by implementation work:

- SPDX license and legal/release approval;
- public naming, security-contact, and disclosure decisions;
- an authorized production pilot;
- representative pre-registered A/B evidence and external claims;
- npm publication, GitHub release, or deployment.

CI, package inspection, release metadata drafts, and verification records may
be prepared without crossing those gates.

## 3. Progressive budget contract

`ContextPlanRequest` keeps its existing `budget` field as the initial selection
ceiling. It may add the optional, versioned field:

```ts
progressive_budget?: {
  soft: ContextBudgetLimitsV03;
  hard: ContextBudgetLimitsV03;
}
```

The invariant is `budget <= soft <= hard` for items, bytes, and estimated
tokens. Absence preserves the current single-ceiling behavior.

The zero-configuration path derives the three token ceilings from the selected
task-type configuration. Byte and item ceilings grow monotonically and never
exceed the existing v0.3 hard caps. The initial selection uses `budget`.
Explicit expansion may grow through `soft` and then `hard`; it must record the
effective tier. A denied or duplicate-only expansion does not change package,
selection digest, or cumulative budget.

## 4. Selection and policy semantics

Core must:

1. retain explicit required evidence and applicable operational policy first;
2. cover explicit required terms deterministically;
3. stop once required evidence is covered, no unresolved authority review
   remains, and the next candidate has no required marginal value;
4. emit an explicit stable omission/stop reason instead of filling the budget
   solely because a candidate has freshness or generic relevance score;
5. preserve path-level satisfaction for exact duplicate required sources
   without counting duplicate payload bytes twice during initial selection;
   during expansion, every previously selected ID remains selected and a newly
   mandatory duplicate alias is added as a separate bounded item when it fits;
   otherwise the prior selection remains intact and insufficiency is explicit;
6. distinguish potential authoritative variants from proven semantic
   contradiction;
7. compute authority effects only from Core-recognized provider/evidence
   combinations. Optional adapter claims cannot promote themselves.

Operational policy applicability is deterministic:

- the root `AGENTS.md` remains mandatory;
- a nearest ancestor `AGENTS.md` applies to a targeted path and its scope,
  including a physical path made relevant by query or criterion discovery;
- `SECURITY.md` is mandatory only for security-relevant task types, terms, or
  target paths, or when explicitly required;
- `CODE_OF_CONDUCT.md` is governance material and is not mandatory execution
  context by default;
- policy excerpts remain subject to the existing byte/line ceilings.

Security relevance is evaluated over the complete bounded normalized request
vocabulary by a deterministic lexical classifier. It must not reuse the lossy
term projection used for ranking, and must conservatively recognize
authentication, credentials, permissions, encryption, dependency security,
vulnerability, audit, advisory, and related security work without making an
unrelated dependency-only task mandatory. This is not semantic classification:
false positives and false negatives remain possible, and an explicit
`required_sources` entry is the override when policy inclusion is required
regardless of wording. Core and the blocked-policy CLI path must use equivalent
rules.

Implicit natural-language acceptance criteria remain mechanical evidence, not
semantic correctness. They must ignore a conservative stopword set and require
more than one discriminative match when more than one discriminative term is
available. Explicit `required_terms` retain `ALL` semantics.

## 5. Truncation and evidence status

Budget status is about budget only. Normal excerpt bounding, provider
truncation, source-collection truncation, and aggregate candidate truncation
must not independently produce `HARD_LIMIT_REACHED`.

Source truncation remains visible through bounded source/truncation outcomes.
Expansion uses `HARD_LIMIT_REACHED` only when the cumulative hard item, byte,
or estimated-token ceiling prevents evidence from being added.

Sensitive or otherwise blocked required evidence must produce a sanitized,
explicit missing/source-failure outcome. It must never expose the path or
content when disclosure would itself be unsafe.

## 6. Agent-facing output

The plain-language `prepare` command emits a compact agent-facing object by
default:

- task and selection identity;
- the prompt-facing `ContextEnvelope`;
- bounded warnings and missing-evidence summary;
- receipt digest, decision counts, and a repository-relative receipt reference;
- next commands for expansion and full inspection.

It does not emit every omitted-candidate decision by default. A separate,
explicit inspection command or compatibility flag may return the full stored
request/receipt. Both forms remain strict process JSON with one document on
stdout and bounded sanitized JSON on stderr.

## 7. Collection, index, and snapshot behavior

One zero-configuration `prepare` operation establishes one accepted-source
observation and reuses it for request creation, optional index preparation, and
compilation. Only that observation may feed selection. A separate bounded
verification-only recollection is permitted immediately before publication to
prove that paths, hashes, omissions, authority, and configuration have not
changed; it must never replace or augment the selection observation.

An accepted observation is untrusted at every exported programmatic boundary.
The implementation must defensively bind and clone every selection-relevant
field, recompute source-body hashes, and validate document, locator, graph,
Repo Map, omission, failure, and configuration identity before candidate
construction or state publication. Retaining an old hash while mutating an
in-memory body or metadata must fail freshness validation.

A validated index/manifest pair with the same accepted-source, schema, policy,
and toolchain identity is reused. Rebuild remains full sibling replacement when
the identity changes. Optional FTS query validation remains bounded and must
not trust unvalidated stored rows.

The accepted-source manifest additionally covers deterministic, screened
configuration sources including package manifests/locks, TypeScript and lint
configuration, supported ecosystem manifests, and conventional extensionless
build files. User-supplied control-plane JSON does not enter the corpus merely
because it has a `.json` suffix. The artifact must call this value an
`accepted_source_digest` unless it also carries an independently defined full
repository-state digest.

Repository identity must not be only a basename. It may use an explicit local
configuration value or a sanitized digest of stable Git/root identity without
persisting an absolute path in public artifacts.

## 8. State integrity and security

- All state-writing commands use the same ignored-state precondition, including
  v0.1 map/task/metrics commands. The precondition reflects effective ordered
  Git ignore semantics and fails closed for later re-inclusions, including
  variant-case rules on case-insensitive repositories.
- Every collector excludes the configured state directory.
- State files use atomic sibling replacement and an exclusive lock where a
  read-modify-write operation exists.
- Locks contain bounded owner metadata and may be recovered only after a
  positive same-host check establishes that the recorded process no longer
  exists. Because Node does not expose a portable atomic compare-and-remove
  primitive, this implementation does not automatically reclaim even a
  positively dead lock: it fails closed and requires an operator to remove the
  exact lock path after separately confirming that no writer is running. A
  malformed or unverifiable lock remains blocking.
- State directories/files request restrictive POSIX modes where supported;
  Windows ACL limitations remain documented and are not misrepresented.
- Optional-adapter timeout is cooperative unless work is isolated. The caller
  must not publish rollback/replacement state while timed-out work can still
  mutate that state.
- Canonical hashing rejects undefined values, symbols, non-enumerable or
  accessor properties, array extras, hostile prototypes, cycles, excessive
  depth, and excessive values.
- Public error details are sanitized; complete Authorization Basic/Bearer
  credentials and raw sensitive details are not exposed in message, details,
  stderr, or a serializable public property.
- Outcome records reject duplicate `run_id` for the same task/selection and use
  an ordered digest chain so removal or reordering is detectable.

## 9. Replay, ablation, and receipt precision

Ablation must preserve or recompute all insufficiency dimensions needed to
avoid a false `READY`, including missing required sources/terms, conflict,
budget, and source-failure state. Experimental artifacts remain explicitly
non-causal.

Receipt validators recompute all invariants that are possible from the receipt
and envelope, including score-component totals, links, selected decisions,
budgets, and digests. Documentation must describe the receipt as an auditable
selection record, not a self-contained proof of semantic correctness or a
replacement for the original request/corpus.

Duplicate groups are complete, disjoint, and non-self-referential. Every
`OMIT_DUPLICATE_CONTENT` decision belongs to exactly one group and names a
distinct representative whose decision is `INCLUDED`; no omitted
representative, orphan `duplicate_of`, overlap, or representative-as-duplicate
is accepted.

## 10. Operability and release preparation

The repository adds CI for supported Node 22.13+ and Node 24 using clean install,
typecheck/contracts, tests, build, package dry-run, Markdown-link validation,
and diff checks. The demo must assert its expected evidence, linkage, cleanup,
and fallback behavior before printing `PASS`.

Package metadata may be prepared, but every package remains private and no
license field is invented until the human license gate is resolved.

## 11. Acceptance criteria

| ID | Required evidence |
|---|---|
| CON-01 | Initial selection is bounded by initial; expansion can reach soft/hard but never exceed hard |
| CON-02 | Root/query-discovered target policy applicability is deterministic, security relevance is independent of ranking truncation, and default governance context tax is avoided |
| CON-03 | A successful zero-config prepare uses one defensively bound accepted-source observation for selection, a verification-only recollection for freshness, and a fresh index |
| CON-04 | Default prepare output omits the full receipt and has an explicit hard byte ceiling |
| CON-05 | Increasing budget alone does not add zero-marginal evidence after mechanical sufficiency |
| CON-06 | Budget, excerpt, provider, source, and aggregate truncation no longer share one hard-limit meaning |
| CON-07 | Duplicate required paths, monotonic retained expansion IDs, complete duplicate groups, blocked required evidence, and potential authority variants are explicit |
| CON-08 | Implicit criterion coverage cannot be satisfied by one generic term when discriminative terms exist |
| CON-09 | Accepted-source digest changes for supported dependency/configuration changes and ignores control state |
| CON-10 | Ablation cannot become READY while another insufficiency remains |
| CON-11 | Optional-provider authority claims cannot change policy authority score or conflict grouping |
| CON-12 | Stale-lock, effective Git-ignore, timeout, permission, atomic-write, duplicate-outcome, error-redaction, receipt-link, and canonical-JSON regressions pass |
| CON-13 | Demo assertions, Node CI matrix, package dry-run, links, post-remediation security scan, and immutable verification record are present |
| CON-14 | Complete v0.1/v0.2/v0.3 compatibility suite, typecheck, build, and disposable CLI smoke pass |

Every behavioral correction begins with a failing public or stable-seam test.
Performance claims require a controlled measurement; source inspection alone
does not establish user-visible speedup.
